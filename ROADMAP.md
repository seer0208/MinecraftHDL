# MinecraftHDL Next Roadmap

This repository contains two distinct tracks:

- `src/main/...`: the original Minecraft Forge 1.10.2 implementation.
- `src/mhdlc/...`: the new standalone phase-1 compiler scaffold.

The modernization strategy is to preserve the legacy code as reference material while building a reproducible EDA-style compiler core outside Minecraft first.

## Current State

The existing project already has the right high-level idea:

`Verilog -> Yosys JSON -> graph -> layered gates -> routed redstone -> Minecraft world`

The main technical constraints in the current repo are:

- The compiler pipeline is invoked directly from the Forge block runtime in `src/main/java/minecrafthdl/block/blocks/Synthesizer.java`.
- Physical generation is represented as Minecraft block state objects in `src/main/java/minecrafthdl/synthesis/Circuit.java`.
- Yosys JSON is parsed straight into an ad hoc graph in `src/main/java/GraphBuilder/GraphBuilder.java`.
- Redstone gates are encoded as hardcoded Java block macros in `src/main/java/minecrafthdl/synthesis/LogicGates.java`.
- There is no standalone build, CLI, CI-ready test harness, or explicit validation layer.

## Phase 1 Goal

Build a standalone compiler foundation that can:

1. Import Yosys JSON.
2. Normalize it into a stable internal netlist IR.
3. Run structural validation for simple combinational designs.
4. Emit normalized JSON for downstream placement/routing work.
5. Produce a lightweight graph export for inspection.

This phase does not attempt:

- Minecraft integration
- schematic export
- placement/routing
- timing analysis
- sequential support

## Phase 1 Deliverables

- `pyproject.toml` with a CLI entrypoint
- `src/mhdlc/` package scaffold
- `mhdlc import` command
- `mhdlc validate` command
- `mhdlc modules` command
- `mhdlc graph` command with DOT output
- design-level import/validation for multi-module Yosys JSON files
- `tests/` for importer, validation, and CLI smoke coverage
- GitHub Actions CI
- starter docs and examples

## Proposed Architecture

```text
src/mhdlc/
  cli.py
  ir/
    netlist.py
  frontends/
    yosys_json.py
  checks/
    validation.py
  export/
    dot.py
  io/
    json_io.py
```

IR layers planned across later phases:

1. Logical netlist IR
2. Redstone technology netlist
3. Physical placed/routed layout

## Phase 1 Work Plan

### Milestone 1: Compiler Skeleton

Status: scaffolded in this change.

Tasks:

- establish standalone package layout
- add CLI entrypoint
- keep dependencies minimal and reproducible
- preserve legacy Java tree in place

### Milestone 2: Yosys JSON Import

Status: scaffolded in this change.

Tasks:

- load a Yosys JSON file
- select a module explicitly or default to the first module
- normalize ports, cells, and net usage into internal dataclasses
- map supported Yosys cell types into stable internal cell kinds

Initial supported cells:

- `AND`
- `OR`
- `XOR`
- `INV`
- `MUX`

Phase-1 rule:

- reject unsupported cells explicitly instead of silently continuing
- preserve net alias metadata even when the backend does not lower it into gates

### Milestone 3: Structural Validation

Status: scaffolded in this change.

Checks:

- single-driver nets
- undriven sinks
- unsupported cells
- combinational loop detection

Phase-1 scope:

- acyclic combinational netlists only

### Milestone 4: Inspection Outputs

Status: scaffolded in this change.

Outputs:

- normalized JSON IR
- validation report in the CLI
- DOT graph export for quick visualization

## Phase 2

After phase 1 is stable:

1. Introduce a data-driven redstone cell library.
2. Characterize cells with footprint, pins, orientation, and delay ticks.
3. Build placement and routing outside Minecraft.
4. Add DRC and tick-based timing reports.
5. Export schematics before returning to a modern Minecraft integration.

## Suggested Near-Term Backlog

1. Expand the importer to support more Yosys primitives and flattened assigns.
2. Add width-aware validation for buses and per-port expectations.
3. Define the redstone cell library file format.
4. Add a stable sample corpus generated by pinned Yosys scripts.
5. Decide whether the long-term runtime stays Python or moves to Rust/Go after the IR stabilizes.
